### A1.4 Why the evidence also argues against the withdrawn sentence (failure analysis only)

The legacy outbound chain (parasut-write-api, create-customer-command, write-client, provider wrapper, verifier, repositories, migration) was read to see how it fails. It is not a design to improve or copy. Findings PWA-01 to PWA-16 below show, among other things:
- the "idempotency key" is an ERP-local string; the HTTP request to the provider carries no idempotency header or client reference (PWA-05), so a timeout leaves an outcome that is unknown by construction;
- three independent routes classify a request that probably reached the provider as a plain failure (PWA-06, PWA-07, PWA-08), which invites a second creation;
- permission and flag checks run after the provider token has already been requested (PWA-02);
- a replay with the same key but a different payload returns the earlier record (PWA-04);
- the lifecycle has no lease, timeout or reconciliation for a stuck "sending" state (PWA-09, MIG-09).
A dry-run mode would not address any of these, because none of them occurs in the request-construction step.

## A2. Summary of results

1. Policy: report section 6.5 item 5 is withdrawn (A1). Item 6 and Q17 are clarified: no credential now. Application development remains unstarted.

Tenancy has two competing authorities in code (erp_users.accessible_company_ids versus companies and company_memberships), and repository comments say production has no companies table while a migration creates and seeds one. ## A7. Consequences for the ERP 3.0 requirements baseline (bounded proposals)

These add specificity to report section 6. They are proposals for the requirements baseline, each needing owner confirmation; none is an implementation instruction, none invents a financial rule, and none concerns a provider write.

1. Integration scope: Parasut is an inbound, read-only source under the current authorization. No legacy outbound artifact (function, schema, capability flag, wrapper, test) is carried into ERP 3.0. Keep an explicit exclusion list so reviewers can check it.
2. Documents with lines (quotes, orders): persist header, lines, totals and number in ONE server-side transactional operation; the browser sends inputs only; the server computes totals; database constraints check them. The rules (rounding, VAT, discount order) are owned by the accountant (Q9-Q12).
3. Lists: use keyset pagination or a stable composite key with a unique tie-breaker; show loaded count and total; distinguish error from empty; never truncate silently; fail loudly when a cap is hit.
4. Money: no coercion of malformed input to zero in any layer; a corrupt amount renders as an error state; one arithmetic implementation; rounding declared per document type by the accountant.
5. Tenancy: one tenant authority with referential integrity (decide Q1 and Q43); policies covered by role-based database tests that run in CI; no policy that is unconditionally true for authenticated users; storage policies scoped like table policies.
6. Identity: bind by immutable user id only; no e-mail fallback; one matching rule everywhere.
7. Governance: a migration's header and its directory must agree; CI fails on "PROPOSED" or "NOT APPLIED" markers in the applied directory; guard tests must not depend on checkout directory names and must fail when they scan zero files.
8. Ordering: authorization, feature gates and configuration checks run before any credential use or outbound contact in every function.
9. Definitions before code: overdue (business day, time zone), amount semantics per document type (VAT basis), currency vocabulary (ISO 4217 with an explicit mapping from vendor codes). These are owner decisions (Q44-Q46).
10. Evidence marked "contrast" (cheque invariants, the row-locking inventory RPC) may inform requirements; it is not code to reuse.
